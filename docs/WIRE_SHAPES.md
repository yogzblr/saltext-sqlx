# Wire shapes

What the databases and drivers actually do, observed by task T1 on 2026-10-29 and, for Oracle and SQL Server, by task T1b on
2026-10-31 (sections 14 and 15); section 16 (pg8000 against psycopg) was observed on 2026-11-01. Rule R18: nothing here is taken from
documentation. A case that could not be executed is marked **NOT RUN** with the reason; it is never filled in.

Sections 0-11 were generated by `scripts/probes/render_wire_shapes.py` from the JSON in `docs/wire_shapes/` (raw output of
`scripts/probes/probe_<dialect>.py`); T1b edited their Oracle and SQL Server rows by hand to point at sections 14 and 15, and
sections 12-16 are written by hand. Running the renderer again would drop those edits and sections.

Environment: Ubuntu 24.04 x86_64, Python 3.13.16, no Docker images (registry access is blocked, section 0), databases
started natively by `tests-support/up.sh`. Accounts: `ro` (SELECT only) and `rw` (DML) on schema `scratch`, over TCP on
127.0.0.1. Statements are issued the way the module will issue them: caller SQL through `text()` with binds; the
module's own statements through `exec_driver_sql()`; one engine per run with `NullPool`.

How to read the exception columns. *SQLAlchemy exception* is `type(e)` of what `engine.connect()` / `conn.execute()`
raised, in `sqlalchemy.exc`; "(not SQLAlchemy)" means the exception reached the caller unwrapped. *Driver exception*
is `type(e.orig)`. *Fields* lists the attributes the driver exception carries (`args(...)` are the positional
argument types; `diag{...}` is psycopg's diagnostics object; `args[0]{...}` is oracledb's error object). *Password in
exception text* is true if the account password appeared in `str(e)`, `repr(e)`, `repr(e.orig)`, `repr(e.orig.args)` or
the formatted traceback (wrong-password case: the wrong password). *SQL text in `str(exc)`* is whether SQLAlchemy's own
`str()` of the exception contains the statement (it appends `[SQL: ...]`).

## 9. What the observations mean for the contract

Each item cites the table that proves it. Items marked *SPEC* were wrong or unlabelled in `SPEC.md` and were corrected in
the same change.

1. **Only three of five databases could run.** PostgreSQL 16.15, MySQL 8.0.46 and MariaDB 10.11.14 ran every case.
   Oracle and SQL Server could not be started (section 0), so every server-side Oracle and SQL Server row was **NOT RUN** in T1; T1b ran them (sections 14, 15).
   Their only real rows are the client-side connection failures, which need no server. Versions other than the ones
   listed in section 0 were not tested (for example MySQL 5.7, MariaDB 11, PostgreSQL 17).
2. **PostgreSQL connect-phase errors have no SQLSTATE.** Wrong password, unknown database and unreachable port are all
   `psycopg.OperationalError` with `args(str)`, `sqlstate` absent and an empty `diag` (section 1, cases 8, 9, x1). They
   differ only in message text (`FATAL:  password authentication failed ...`, `FATAL:  database ... does not exist`,
   `Connection refused`). *SPEC* listed "PG 28P01/28000" as the E_AUTH_FAILED source; that code is not observable here.
3. **PyMySQL does not map errors to classes the way SQLSTATE classes suggest.** Missing column (1054) and permission
   denied (1142) arrive as `OperationalError`, not `ProgrammingError`; division by zero in DML (1365) is
   `OperationalError`, not `DataError`; a bad bound integer (1366) is `DataError`. `SQLSTATE` is available on server
   errors (`exc.orig.sqlstate`, also on PyMySQL 1.2.3) but is `None` for client-side failures (2003, 2013). The same
   situation differs between servers: error 1366 has SQLSTATE `HY000` on MySQL and `22007` on MariaDB; the timeout errors
   are `HY000` (MySQL 3024) and `70100` (MariaDB 1969). Mapping must therefore use the vendor code first (R2), and a
   class-42 rule would wrongly classify "access denied to database" (1044, SQLSTATE 42000) as a SQL error.
4. **`SELECT 1/0` is not an error on MySQL or MariaDB.** It returns `NULL` (section 1, case 4). The error (1365, SQLSTATE 22012)
   only appears in a data-changing statement (case 4b), so a "division by zero" check on these servers needs DML or a
   different statement. PostgreSQL raises in both forms.
5. **Statement timeout is per dialect and has traps** (section 2).
   - PostgreSQL: `SET statement_timeout = 300` cancels after 0.3 s with 57014, as before.
   - MySQL 8.0.46: `SET SESSION MAX_EXECUTION_TIME=300` interrupted `SELECT SLEEP(3)` after 0.3 s **without raising an error**
     (the statement returned `1`). A `SELECT` over a table did raise 3024 (`OperationalError`, SQLSTATE `HY000`). An
     `INSERT ... SELECT SLEEP(1)` was not interrupted at all (1.0 s, no error). `max_statement_time` is an unknown variable on
     MySQL (1193).
   - MariaDB 10.11.14: `SET SESSION max_statement_time=0.3` (seconds; the fractional value was accepted and read back as
     0.3) raised 1969 (SQLSTATE `70100`) for `SELECT SLEEP`, `SELECT ... FROM table` **and** `INSERT ... SELECT`.
     `MAX_EXECUTION_TIME` is an unknown variable on MariaDB (1193). SQLAlchemy reports `dialect.is_mariadb` as `False` on MySQL and
     `True` on MariaDB, which is a usable way to choose the variable.
   - PyMySQL `read_timeout=1` is a client-side alternative: it raised `OperationalError` 2013 after 1.0 s (message
     differs by server: `The read operation timed out` vs `timed out`). Whether the server kept running the statement
     afterwards was not observed.
   - Oracle `call_timeout` and pymssql `timeout`: NOT RUN in T1; observed in T1b (DPY-4024 / DPY-4011; DB-Lib 20003), sections 14-15.
   - Connect timeouts were **not** demonstrated: connecting to 192.0.2.1 returned immediately (`Connection refused` for
     PyMySQL, oracledb, pymssql; `server closed the connection unexpectedly` for psycopg), so the sandbox network does not
     black-hole addresses.
6. **No in-session read-only guard held on any runnable dialect** (section 3). Every guard refused a plain write
   (PG 25006; MySQL/MariaDB 1792, SQLSTATE 25006), and every guard was bypassed by at least one statement a caller can send through `query`:
   - PostgreSQL: `SET TRANSACTION READ WRITE`, and `COMMIT` then write, and the same flip after a connection-level
     `default_transaction_read_only=on` (this reproduces the earlier result).
   - MySQL: `SET SESSION TRANSACTION READ ONLY` is bypassed by `SET SESSION TRANSACTION READ WRITE`,
     `SET TRANSACTION READ WRITE`, `START TRANSACTION READ WRITE` and `SET SESSION transaction_read_only=0`; it survives `COMMIT`.
     `SET TRANSACTION READ ONLY` (next transaction only) is also bypassed by `COMMIT` then write. `START TRANSACTION READ ONLY`
     resisted `SET SESSION ... READ WRITE`, `SET TRANSACTION READ WRITE` (error 1568) and `transaction_read_only=0`, but not
     `START TRANSACTION READ WRITE` or `COMMIT` then write. The server variable `tx_read_only` is unknown (1193).
   - MariaDB: same pattern; the variable is `tx_read_only` (`transaction_read_only` is unknown, 1193) and it bypasses the
     guard.
   - A guard set through PyMySQL `init_command` is bypassed the same way as a statement guard.
   - Oracle `SET TRANSACTION READ ONLY` and SQL Server: NOT RUN in T1; T1b: Oracle refuses writes (ORA-01456) and is bypassable by a PL/SQL block; SQL Server has no guard (sections 14-15).
   The `ro` account was refused by the database for INSERT, UPDATE, DELETE and CREATE TABLE and for SELECT in an
   unrelated schema on all three (section 1, cases 6, 6b-6e). A write by `rw` through a transaction that is rolled back did not persist
   (case x4).
7. **Not everything that reaches the caller is a `DBAPIError`.** Observed raw exceptions: `TypeError` on first connect to a
   SQL_ASCII PostgreSQL database (section 7, same text as BUILD_PROMPT); `RuntimeError` and `AttributeError` from PyMySQL
   authentication (section 6); `ValueError` from `exec_driver_sql` with a literal `%` under PyMySQL (section 5);
   `sqlalchemy.exc.StatementError`/`InvalidRequestError` for a literal colon bind trap. `errors.translate` has to
   catch `Exception` around connect and execute, not only `DBAPIError`.
8. **Error text can contain data and the statement.** `str(sqlalchemy_exc)` appends `[SQL: ...]` and, for statements with binds,
   `[parameters: ...]` including the bound values (x3 rows). The server's own message can also echo a bound value
   (PostgreSQL 22P02 primary message, MySQL/MariaDB 1366) and, on MySQL/MariaDB, a row value in the *primary* message
   (`Duplicate entry 'a@example.com' ...`, 1062). PostgreSQL keeps that value in `diag.message_detail`
   (`Key (email)=(a@example.com) already exists.`), which `error_detail: false` can drop. The primary message of the
   other two cannot be filtered that way.
9. **No password appeared** in `str(e)`, `repr(e)`, `repr(e.orig)`, `repr(e.orig.args)` or the formatted traceback for any
   observed case on PostgreSQL, MySQL, MariaDB, nor in the Oracle and SQL Server connection-failure rows. This covers the
   cases in section 1 only; successful-connect logging and driver debug output were not examined.
10. **PyMySQL 1.2.3 negotiated TLS with MySQL 8 without being asked** (cipher `TLS_AES_256_GCM_SHA384`, section 6). The server
    certificate is auto-generated and self-signed, so the connection was encrypted but no certificate was verified by
    the caller. With `ssl_disabled=True`, MySQL 8's default `caching_sha2_password` needs the `cryptography` package:
    without it PyMySQL raises `RuntimeError`; with it, the first connection after `FLUSH PRIVILEGES` raised
    `AttributeError: 'NoneType' object has no attribute 'is_auth_switch_request'` and the next succeeded. MariaDB
    (`mysql_native_password`) never needed it. `oracledb` declares `cryptography>=3.2.1` as a dependency and PyMySQL has an
    optional `rsa` extra for it (package metadata), so the Oracle extra brings it in; the MySQL extra alone does not.
11. **SQLAlchemy 2.1.6 behaved identically to 2.0.55** on every record for PostgreSQL, MySQL and MariaDB, and for the
    client-side Oracle and SQL Server records (section 8). The `text()` traps still occur on 2.1.6: `:a::int` is not a bind,
    `'{"a":1}'` raises `A value is required for bind parameter '1'`, `\:` escapes it, `CAST(:a AS ...)` and `%` inside
    `text()` work, and compiled output is identical on all five dialects. Only the documentation URL in SQLAlchemy's
    error text changed (`/e/20/` to `/e/21/`).
12. **`text()` and `%`.** On PyMySQL, SQLAlchemy doubles `%` in `text()` (`%%`) and the statement works; `exec_driver_sql`
    with a literal `%` raised `ValueError` (PostgreSQL/psycopg raised `psycopg.ProgrammingError`). For pymssql the
    compiled statement keeps a single `%` although its paramstyle is `pyformat`; whether that breaks a statement that
    has both a literal `%` and binds was NOT RUN in T1; T1b: it works (section 15).
13. **Types** (section 4): MySQL and MariaDB return `str` for the JSON column (MariaDB stores it as `LONGTEXT`; MySQL has a
    JSON type but `text()` still returned `str`) and for the `CHAR(36)` identifier, `bytes` for `BINARY`/`VARBINARY`,
    `Decimal` for `DECIMAL`, `datetime` (microsecond precision kept) for `DATETIME(3)`, `None` for NULL. Neither has a
    native UUID type, so the seed uses `CHAR(36)` and `BINARY(16)`. PostgreSQL returned `dict` and `UUID` for `jsonb` and
    `uuid`. Oracle and SQL Server: NOT RUN in T1; T1b types in sections 14-15.

Findings (Oracle):

- **Timeout** (`Connection.call_timeout`, ms, client-side): a query over the limit fails with `DPY-4024: call timeout of 500 ms
  exceeded` after 584 ms; a PL/SQL call (`dbms_session.sleep(3)` with 300 ms) ended with `DPY-4011 ... socket timed out while
  recovering from previous socket timeout` (the driver gave up on the connection). Both are `E_TIMEOUT`. A statement cannot
  lift a client-side limit. Connect timeout `tcp_connect_timeout` (s): `DPY-6005 ... timed out` after 3001 ms for 3 s.
- **In-session read-only** (`SET TRANSACTION READ ONLY`, first statement of the transaction): an insert is refused with
  ORA-01456; `SET TRANSACTION READ WRITE` afterwards is ORA-01453; `commit` as a statement ends the read-only transaction (no
  error). **Bypass observed:** `begin commit; insert into scratch.e2e_notes ...; commit; end;` after the guard persisted the row
  (case `read_only_bypass_plsql`, checked from a new connection, `read_only_bypass_check` = 1). Without the final `commit`
  the insert is rolled back by the module (`t1_bypass_plsql_block_check` = 0). The database role is the control.
- **Role**: `ro` is refused for UPDATE/DELETE (ORA-41900 `missing <verb> privilege`, the 23ai wording), CREATE TABLE
  (ORA-01031) and a table it was not granted (ORA-00942, as if the table did not exist). `rw` writes rolled back left nothing.
- **One statement per call**: a second statement after `;` is ORA-03405; a trailing `;` is accepted.
- **NUL**: `select 'a\x00b' from dual` and a bound `a\x00b` both return the full value (no truncation on Oracle).
- **text() traps**: `:a::int` reaches the driver as written and python-oracledb reports an unbound placeholder (DPY-4010);
  `'{"a":1}'` is the SQLAlchemy `A value is required for bind parameter '1'` trap; `\:` works; `%` is harmless, also through
  `exec_driver_sql`; `CAST(:a AS int)` works.
- **Unknown host**: `socket.gaierror(-2, 'Name or service not known')` escapes python-oracledb unwrapped (not a `DBAPIError`).
- **Types** (`type_probe`, `ro`): `NUMBER(10,2)` Decimal `12.5`; `TIMESTAMP(6)` datetime with microseconds; `RAW(16)` bytes;
  `BLOB` bytes (read by SQLAlchemy); native `JSON` dict with Decimal numbers (`{'a': Decimal('1'), 'b': [True, None]}`);
  `NVARCHAR2` str (non-ASCII kept); NULL None. Column names lower case; `count(*)` without an alias is `count(*)`.
- **Server version**: `Connection.version` = `23.26.2.0.0` (no query needed).

- **Timeout** (pymssql connect argument `timeout`, whole seconds, client-side): `waitfor delay '00:00:03'` and a long SELECT both
  fail after 1.0 s with DB-Lib 20003 `TDS server connection timed out` followed by 20047 `DBPROCESS is dead or not enabled`; the
  reported number is 20047 and the connection is unusable afterwards. `E_TIMEOUT`. Connect timeout `login_timeout`: 20009 `...
  Connection timed out (110)` after 3001 ms for 3 s. `SET LOCK_TIMEOUT` is accepted but limits only lock waits.
- **No in-session read-only**: `rw` writes inside the rolled-back transaction left nothing (`t1_rw_write_then_rollback_check` =
  0); there is no guard statement (`SET TRANSACTION ISOLATION LEVEL SNAPSHOT` is not one).
- **Batches**: `insert ...; insert ...` and `insert ... insert ...` (no separator) both ran and committed two rows
  (`multi_statement_check`, `multi_statement_no_sep_check` = 2); `insert ...; commit` persisted the row although the probe rolled
  back (`commit_inside_check` = 1); `select 1; select 2` returns a second result set (`cursor.nextset()` True), two inserts do
  not. This is why the module refuses a `;` followed by another statement and a second result set on SQL Server (SPEC 4.2).

- **NUL**: pymssql interpolates bound values into the statement text; `select 'a\x00b'` and a bound `a\x00b` both fail with

  scratch.e2e_notes\x00 where id = 99999` deleted every row (rowcount 3; PostgreSQL did the same; MySQL/MariaDB answered 1064,
  Oracle ran the whole statement). The module refuses both (SPEC section 5).
- **text() traps**: `:a::int` is a syntax error (102); the `'{"a":1}'` trap as everywhere; `\:` works; `%` with and without binds
  works.
- **Types** (`type_probe`, `ro`): `decimal(10,2)` Decimal `12.50`; `datetime2(6)` datetime with microseconds;
  `uniqueidentifier` UUID; `varbinary` bytes; `nvarchar(max)` JSON text str; NULL None. `rowcount` is -1 for SELECT.
- **Server version**: `@@VERSION` is several lines (`Microsoft SQL Server 2022 (RTM-CU25) (KB5081477) - 16.0.4255.1 (X64) ...`).

## 16. pg8000 against psycopg (PostgreSQL 16.15, observed 2026-11-01)

Why: pg8000 (pure Python, BSD-3) became the default PostgreSQL driver (SPEC decision D15) so that every platform, including
Windows ARM64 where `psycopg-binary` has no wheel, can run PostgreSQL profiles. Everything below was run on the native
PostgreSQL 16.15 of `tests-support/` (UTF8 database, port 54329, TLS server on 54339), Python 3.14.6, SQLAlchemy 2.0.55,
**pg8000 1.31.6** and **psycopg 3.3.6**, through the module's own `lib/engine.py` / `lib/runner.py` / `lib/errors.py`. The
raw scripts are throw-away probes (not kept); the regression tests that pin each fact are named in brackets.

### 16.1 Stock pg8000 is not safe for this module (what the adapter has to repair)

SQLAlchemy's `postgresql+pg8000` dialect with its default cursor, `rw` account:

| call | observed |
|---|---|
| `select 1; select 2` (no binds) | **ran**: `[(1,), (2,)]` (the simple query protocol) |
| `commit; create table scratch.t(i int)` (no binds) | **ran past the COMMIT**: failed only on `permission denied for schema scratch` (42501), i.e. the second statement was executed (T11 D1 again) |
| `select 1; select :a` (with a bind) | `ProgrammingError {'C': '42601', 'M': 'cannot insert multiple commands into a prepared statement'}` (extended protocol) |
| `select 5 % 3` (no binds) | `[(2,)]` |
| `select 5 % 3, :a` (with a bind) | `InterfaceError ('Only %s and %% are supported in the query.',)` (pg8000 scans for `%` when there are binds) |
| `connect_args={"timeout": 2}`, socket timeout after connect | **2.0**: the connect timeout stays on the socket as the read timeout of every later statement |

So pg8000 chooses the protocol by whether binds are present: the same bypass psycopg had before `prepare_threshold=0` (the read-only
guard, the time cap, the `execute` verb filter and `dry_run` all defeated by `COMMIT; ...`), plus a `%` trap. The adapter
(`lib/dialects.py`, `PostgreSQLPg8000`) therefore:

1. creates the engine with `paramstyle="numeric_dollar"` (SQLAlchemy renders `$1`, `$2`) and replaces the connection's cursor by a
   subclass whose `execute` always calls `Connection.execute_unnamed` (Parse/Bind/Execute, one statement per message) and never
   scans for `%`; observed result: `select 1; select 2` -> `[E_SQL] postgresql 42601: cannot insert multiple commands into a
   prepared statement`, `COMMIT; CREATE TABLE ...` -> the same, nothing created, `select 5 % 3` -> 2, `'%s %d %(x)s'` literal intact
   [`test_a_second_statement_is_refused_by_the_server`, `test_percent_sign_is_data_for_the_driver_not_a_placeholder`];
2. proves it once per process on the first real connection: `SELECT 1; SELECT 2` must be refused with 42601, otherwise every call
   fails with `[E_DRIVER_MISSING]` (fail closed) [`test_a_driver_that_runs_two_statements_fails_closed`];
3. resets the socket timeout to `statement_timeout_ms / 1000 + 1` after the connection is made (observed 5.0 for a 4000 ms limit and a
   2 s connect timeout) [`test_socket_read_timeout_is_the_statement_timeout_plus_a_second_not_the_connect_timeout`];
4. declares the PostgreSQL type of plain bound scalars (16.4) and skips `CLOSE <cursor>` in an aborted transaction (the streaming cursor
   of SQLAlchemy would log a second, misleading error).

`execute_unnamed` is a pg8000 internal, so `pyproject.toml` pins `pg8000>=1.31.5,<1.32` and step 2 guards the rest.

### 16.2 Error shapes

pg8000 raises `pg8000.exceptions.DatabaseError` (SQLAlchemy: `DatabaseError`; at connect time `ProgrammingError` or `InterfaceError`) with **one dict in `args[0]`**, not attributes: `{'S': 'ERROR', 'V': 'ERROR', 'C': '42P01', 'M': 'relation
"nope" does not exist', 'P': '15', 'F': 'parse_relation.c', 'L': '1449', 'R': 'parserOpenTable'}`. `D` (detail) and `H` (hint)
appear when the server sends them. `lib/errors.py` reads `C`, `M`, `H`, `D` and ignores the source-position keys. Real results through
`errors.raise_for` (the same call, both drivers):

| case | psycopg 3.3.6 | pg8000 1.31.6 |
|---|---|---|
| missing table | `[E_SQL] postgresql 42P01: relation "nope" does not exist` | identical |

Differences that needed code:

- **Connect failures carry the server's SQLSTATE** with pg8000 (28P01 wrong password / unknown role, 3D000 unknown database,
  28000 for `pg_hba.conf` and client-certificate refusals, 57P03 starting up); psycopg gave none (section 13). `_PG_EXACT` maps
  3D000, 53300 and 57P01/02/03 to `E_CONNECT`; for a FATAL error or class 28/08 the message text is looked at first, because class 28
  is both `E_AUTH_FAILED` (bad password) and `E_CONNECT` (`no pg_hba.conf entry`, the PR #5 mapping). Only 28P01 and 3D000 were
  observed; the other states are the documented ones.
- **A socket failure is one `InterfaceError`** whose text is `Can't create a connection to host H and port P (timeout is 2 and
  source_address is None).` and whose `__cause__` is the OS error: `ConnectionRefusedError(111, 'Connection refused')`,
  `TimeoutError('timed out')` (blackhole host 10.255.255.1, 2 s), `socket.gaierror(-2, 'Name or service not known')`. `errors._pg8000_connect`
  rebuilds a psycopg-like `connection to server at "H", port P failed: <reason>` from the cause (`timeout expired` for a timeout:
  still `E_CONNECT`, not `E_TIMEOUT`).
- **No password**: with SCRAM and `password=None` pg8000 fails with a bare `AttributeError: 'NoneType' object has no attribute
  'decode'` (the same with `password=""`); for other methods it raises `InterfaceError("server requesting password authentication,
  but no password was provided")`. A `do_connect` hook turns the first into the second [`test_do_connect_turns_the_scram_attribute_error_into_the_no_password_message`].
- **pg8000 reads neither `$PGPASSWORD` nor `~/.pgpass`** (observed: `PGPASSWORD` set, profile without password -> the error above;
  psycopg connected). So the `password_dropped` guard (SPEC 3.2) has nothing to block and the psycopg-only
  `password=""`/`passfile` arguments are not sent [`test_pg8000_never_offers_the_minions_environment_or_passfile`].
- **Unix-socket host** (`host: /var/run/postgresql`): pg8000 tries to resolve it as a name (`gaierror`) because it takes `unix_sock`
  instead; profile hosts are TCP host names, so this is unsupported with pg8000 (psycopg connects). Not offered.
- **Statement error mid-stream**: `SELECT 10 / (i - 3) FROM generate_series(1,5) i` -> `[E_SQL_DATA] postgresql 22012` and the next
  call works, for both drivers.

### 16.3 TLS (`ssl_certs_dir`, `ssl_mode`) with pg8000

pg8000 takes `ssl_context` (an `ssl.SSLContext`), not libpq parameters. `tls.pg8000_context` builds it from the same files:
`ssl.create_default_context(cafile=<profile CA>)` (only that CA is trusted; the system store is not loaded),
`check_hostname = (ssl_mode == "verify-full")`, `load_cert_chain(cert, key)` when a client pair exists. The unit tests use stand-ins;
the handshakes below ran against the TLS server of `tests-support/tls` [`tests/functional/test_tls_functional.py`, 32 passed with each driver]:

| case | psycopg (libpq) | pg8000 (Python `ssl`) |
|---|---|---|
| verify-full, CA + client pair | connects | connects |
| verify-ca, host `127.0.0.2` (not in the SAN) | connects | connects |
| verify-full, host `127.0.0.2` | `[E_CONNECT] postgresql: ... server certificate for "localhost" ... does not match host name "127.0.0.2"` | `[E_CONNECT] postgresql: [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: IP address mismatch, certificate is not valid for '127.0.0.2'.` (an unwrapped `ssl.SSLCertVerificationError`) |
| wrong CA | `certificate verify failed` | `[SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: self-signed certificate in certificate chain` |
| expired client certificate | `... alert certificate expired` | `InterfaceError('network error')` <- `SSLZeroReturnError` <- `SSLError(1, '[SSL: SSLV3_ALERT_CERTIFICATE_EXPIRED] ssl/tls alert certificate expired')`: mapped to `E_CONNECT` with the alert text |
| client certificate from another CA | `... alert unknown ca` | same shape, `[SSL: TLSV1_ALERT_UNKNOWN_CA] tlsv1 alert unknown ca` |
| CA only, role needs a certificate | `E_AUTH_FAILED ... connection requires a valid client certificate` | the server's own `{'C': '28000', 'M': 'connection requires a valid client certificate'}` -> `E_AUTH_FAILED` |
| garbage client key / key vanished after profile load | `E_CONNECT` | `ssl.SSLError` / `FileNotFoundError` from `load_cert_chain` while the engine is built -> `E_CONNECT`, no path (`engine.build_engine` now translates errors of `connect_args`) |

The `(_ssl.c:NNNN)` source position of the `ssl` module is removed from PostgreSQL messages. **Without `ssl_certs_dir`** pg8000's default
`ssl_context=None` is opportunistic and unverified: it sends an SSLRequest and wraps the socket with `CERT_NONE` when the server
agrees, and continues in plain text when it does not. That is libpq's default `sslmode=prefer` (observed: `tls_pw` without
`ssl_certs_dir` connects to the TLS-only server, and `pg_stat_ssl` for that session says `ssl = true`, `TLSv1.3`, `TLS_AES_256_GCM_SHA384`). pg8000 has no `disable`: the allowlisted `sslmode`,
`sslrootcert` and `keepalives*` keys of psycopg do not exist for it (`[E_POLICY]`); a profile that needs verified TLS uses `ssl_certs_dir`.

### 16.4 Bound values and returned types

SQLAlchemy renders `text()` binds untyped. psycopg declares a type for each Python value; stock pg8000 declares **none**, so the server
types the parameter from context: `SELECT :a` returned the **string** `"1"` for 1, `"true"` for True, `"1.5"` for 1.5 and `"\x0001ff"`
for bytes, and `SELECT :a + :b` is `operator is not unique: unknown + unknown`. The cursor therefore passes the type OIDs psycopg would
use (`dialects._pg8000_oid`): bool 16; int 21/23/20/1700 by size (the smallest that fits, like psycopg, so `repeat('x', :n)` still
accepts a small `n`); float 701; Decimal 1700; bytes 17; date 1082; datetime 1114/1184; time 1083/1266; timedelta 1186; UUID 2950;
everything else (str, None, list, dict) undeclared. After that, `SELECT :v` gives the same JSON as psycopg for int, bool, float, str,
Decimal, bytes, date, datetime (naive and aware), time, UUID and None [`test_a_bare_bind_comes_back_typed_like_psycopg_returns_it`].

Still different (all observed):

| value | psycopg | pg8000 |
|---|---|---|
| bare `SELECT :a` with a list `[1,2,3]` | `[1, 2, 3]` | `"{1,2,3}"` (undeclared, so text); `CAST(:a AS integer[])` gives `[1, 2, 3]` for both |
| a dict bind | `E_INTERNAL ProgrammingError` (needs a `Json` wrapper) | sent as JSON text; `CAST(:d AS jsonb)` works |
| `'infinity'::timestamp`, `'-infinity'::date`, `'12000-01-01'::timestamp` | `[E_SQL_DATA] postgresql: timestamp too large (after year 10K)` | returned as the strings `"infinity"`, `"-infinity"`, `"12000-01-01 00:00:00"` |
| `'1 mon'::interval` | `"30 days, 0:00:00"` (lossy `timedelta`) | `"1 months"` |
| `'1000000 years'::interval` | `"365000000 days, 0:00:00"` | `"1000000 years"` |
| `'(1,2)'::point` | `"(1,2)"` | `[1.0, 2.0]` |
| `'12:00:00+05'::timetz` | `"12:00:00+05:00"` | `"12:00:00+05"` |
| `'[1,5)'::int4range` | `"[1, 5)"` | `"[1,5)"` |
| `SELECT :a IS NULL` with None, `SELECT :a` with None | NULL | NULL (same) |

Unchanged for both: `CAST(:x AS t)` works, `:x::t` is still `42601`, a literal colon is written `\:`, `NaN`/`Infinity` floats come back as the strings
`"NaN"`/`"Infinity"`, `Decimal` as a string, bytes as `{"$bytes_b64": ...}`, Unicode, 2 000 000-row results are cut at `limit` through the
server-side cursor (SQLAlchemy `stream_results` -> `DECLARE ... NO SCROLL CURSOR`) without reading the rest.

### 16.5 Other observations

- Password with `p@ss:w/o%rd?x#y&=+ "'\é日` connects and fails correctly with pg8000 (`URL.create`); the wrong one is `28P01` without the
  password in the text [`test_password_with_every_awkward_character`].
- `application_name` from `connect_args` is passed as a value (`salt sqlx host=evil port=1` stayed one string).
- `SET statement_timeout` and `SET TRANSACTION READ ONLY` run through the same cursor; with pg8000 the read-only transaction refuses writes with
  25006 as before. The guard is still not a security control: the role is.
- The once-per-process proof statement (`SELECT 1; SELECT 2`, refused with 42601) costs one round trip on the first connection of a process.
- Not run: pg8000 against PostgreSQL 14/15/17/18, against a server with `md5`/`password` authentication, over a Unix socket,
  through PgBouncer, with `ssl_certs_dir` on Windows, and `COPY ... FROM STDIN` (the cursor does not offer `stream=`).

## 17. Host spellings and the link-local check (call-time `host`, observed 2026-11-01, D16)
