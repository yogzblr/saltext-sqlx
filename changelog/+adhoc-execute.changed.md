`sqlx.execute` and `sqlx.psql_query write=True` now work on a connection with no profile (the connection sent in the call), **on by default** (SPEC decision D17, owner decision 2026-11-27), to mimic Salt's own `postgres.psql_query`, which writes whatever it is sent. Before this change such a call was `[E_EXECUTE_DISABLED]` before anything connected. An ad-hoc write behaves like a write on a profile with `allow_execute: true`: it commits (`rows_affected`, `committed`), `dry_run=True` rolls back, one statement per call on every dialect, the hard caps and timeouts apply (a call can only lower them), the password is masked in errors and logs, link-local and cloud-metadata targets are refused and `allowed_hosts` / `allowed_ports` / `allowed_dialects` still apply. The statement must start with a verb in the new `sqlx:_policy:adhoc_execute_verbs` (default INSERT, UPDATE, DELETE, the same default as a profile's `execute_verbs`, so DDL such as CREATE is `[E_POLICY]` until the operator lists it). New operator key `sqlx:_policy:allow_adhoc_execute` (boolean, absent = true): set it to `false` to restore the previous refusal exactly (`[E_EXECUTE_DISABLED] profile '(adhoc)' does not set allow_execute: true`); a malformed value is `[E_POLICY]`. A call can never send `allow_adhoc_execute`, `adhoc_execute_verbs`, `allow_execute` or `execute_verbs` (`[E_OPTION_UNKNOWN]`). `allow_adhoc_connection: false` still means no ad-hoc connection at all, and `allow_call_params: []` still means no connection field can be sent, so neither allows an ad-hoc write. `query`, `check_query_result`, `check_row_count`, `ping` and `table_list` stay read-only and rolled back. **Accepted risk**: anyone who can run `sqlx.execute` on a minion can run write statements against any host it can reach, with credentials they supply; the database account is the real limit. For fleets whose callers are not fully trusted set `allow_adhoc_execute: false` and `allowed_hosts`, and write through named profiles.
